# nixos-config

Personal `den`/flake-parts configuration for three machines.

| Host | System | Role |
| --- | --- | --- |
| `chidi` | `aarch64-darwin` | Work laptop |
| `janet` | `aarch64-darwin` | Personal laptop |
| `tahani` | `x86_64-linux` | Home server |

## Layout

Every `.nix` file under `modules/` is a flake-parts module, auto-imported by import-tree. Underscore-prefixed paths are not imported; they hold data and helpers used by the module next to them.

- `modules/den.nix` — den setup, foundational flake inputs, host inventory, defaults
- `modules/profiles.nix` — `host-*` and `user-*` bundles that hosts include
- `modules/hosts/` — one file per machine
- `modules/features/{system,interactive,development,ai,services,personal}/` — one aspect per capability. Feature-specific flake inputs live in the feature that uses them.
- `modules/_lib/` — user constants, theme palette, one systemd helper
- `secrets/` — SOPS-encrypted files (see `.sops.yaml`)

## Commands

```bash
nix run .#apply                    # sudo {darwin,nixos}-rebuild switch --flake .
nix run .#update -- [input...]     # nix flake update, then regenerate flake.nix
nix build .#darwinConfigurations.janet.system
nix build .#nixosConfigurations.tahani.config.system.build.toplevel
nix fmt
nix flake check
```

Roll back with `darwin-rebuild --rollback` or `nixos-rebuild switch --rollback`.

`flake.nix` is generated by flake-file. After changing a `flake-file.inputs` declaration, run `nix run .#write-flake && nix flake lock && nix fmt`.

Do not bump `system.stateVersion` or `home.stateVersion`.

## Disk maintenance on Tahani

The `disk-maintenance` aspect collects Nix garbage daily while retaining
30 days of generations. Nix also attempts collection during builds when free
space drops below 100 GiB, aiming to restore 200 GiB free.
Systemd cleans `/tmp` after two days unused and `/var/tmp` after seven days,
checking hourly; the journal is limited to 1 GiB.

Docker's default builder collects cache toward a 30 GB budget. Daily pruning
also removes unused images, stopped containers, and cache older than seven
days; volumes are retained.

The development tools aspect installs `mbx` on the user's normal PATH on all
three hosts. Disk maintenance supplies `~/.config/mbx/config.toml` and an hourly
`mbx-gc` user timer on Tahani, using that installed tool. Mr. Boxington shares
a 60 GiB collection budget across its action store,
managed targets, and incremental state, prioritizing temporary targets for
eviction. Targets under `.t3/worktrees` are kept while their checkout exists,
including between worker commands and under disk pressure; deleting the
checkout makes them eligible for collection again. A build lease alone only
protects a target while its mbx command runs, so evicting live worker targets
can leave dangling `target` symlinks between commands.

This is a collection target rather than a hard quota: live T3 worktrees,
active builds, other explicitly protected targets, and the most recent state
can exceed it. Remove finished worktrees to release their protected caches.
Files in unmanaged Cargo targets and worktree source files are outside this
policy. Environment variables such as `MBX_TARGET_KEEP` override the
configuration for the commands that set them.

The policy does not repair links left dangling by earlier collection. From
the affected Cargo workspace, run `mbx build` without a target-directory
override to recreate its managed target and record. Cargo that bypasses mbx,
or a build using `--target-dir` or `CARGO_TARGET_DIR`, does not perform this
repair.

Inspect cleanup with `journalctl -u nix-gc -u docker-prune` and
`journalctl --user -u mbx-gc`. Apply configuration changes with `nix run .#apply`
from this repository; the user timer is enabled through Home Manager.

## CLIProxyAPI on Tahani

CLIProxyAPI runs from a pinned upstream Docker image. Its official management UI
is served at `https://cliproxyapi.manticore-hippocampus.ts.net/management.html`;
the API base URL is `https://cliproxyapi.manticore-hippocampus.ts.net/v1`.
The Tailscale service `svc:cliproxyapi` must be approved in the tailnet, as with
the other Tailscale services. Only the loopback port `8317` is published locally.

Initial credentials are SOPS-encrypted in `secrets/cliproxyapi`. After applying,
retrieve the management key with `sudo cat /run/secrets/cliproxyapi-management-key`
and the client API key with `sudo cat /run/secrets/cliproxyapi-api-key` on Tahani.
Connect provider accounts through the web UI; no provider accounts are preconfigured.

The initial configuration is copied once into `/var/lib/cliproxyapi/config.yaml`.
Web UI settings, authentication files, and downloaded UI assets persist in that
directory across restarts and upgrades. Later edits to the Nix seed or SOPS keys
do not overwrite the live configuration; rotate live keys through the UI and
update the encrypted seed separately. The UI assets follow upstream automatic
updates independently of the pinned server image.

## OpenCode 2

All three workstation users receive `opencode2` from `llm-agents.nix`, with
self-updates disabled so Nix owns upgrades. Its Home Manager configuration
reuses the shared MCP servers and skills, including Home Assistant's OAuth
client settings. Host-specific skills under `~/.agents/skills` are discovered
automatically.

The only configured plugin is `@ex-machina/opencode-anthropic-auth`, pinned to
the v2-compatible `2.0.0-next.6` release. After applying, launch `opencode2`, run
`/connect`, and select **Anthropic → Claude Pro/Max** to sign in.

## Optional manual browser pane on Tahani

The terminal-browser v0.13.4 package remains available on Tahani. Its local
skill is explicit only: `/skill:terminal-browser`. It does not compete for
generic browser tasks. In a supported terminal multiplexer:

```sh
terminal-browser open --split right http://localhost:3000
```

Browser instances share the user daemon/profile. A local `--ssh tahani`
browser only proxies network requests. SSH/Ghostty graphics, mouse input,
and screenshot return remain unverified; no live SSH stall fix is claimed.

Nix owns legacy setup/upgrades, with telemetry/update polling and mutable setup
blocked. Stable `terminal-browser-nix` XDG state is not migrated from mutable
installations. Close owned panes before changing package versions and wait for
the daemon to exit (upstream schedules 15-second idle exit; its generation check
is unreliable with Nix timestamps). Never automate `terminal-browser shutdown`:
it closes every legacy browser. No always-on browser service is introduced.

## Neovim reviews

The workstation profile includes the full Neovim configuration on all three
hosts. Neovim uses Zsh; VS Code keeps its separate Neovim init and integrations.

CodeDiff provides inline diffs and integrates with Neogit. Use
`<leader>vd` for the current file, `<leader>vD` for all changes, or
`<leader>vR` to compare the branch with `origin/HEAD`.

Use code-review.nvim to collect feedback:
- `<leader>rc` comments on the cursor line or visual selection; submit with Ctrl+Enter.
- `<leader>rp` previews the review; `<leader>rl` lists comments.
- `<leader>ry` copies structured Markdown with filenames, line numbers, and code context.
- Paste into your coding agent and ask it to address the feedback.
- `<leader>rw` saves a review to a file instead; `<leader>rx` clears comments.

Comments persist in the project's `.code-review/` directory. Clipboard export
uses Neovim's OSC52 provider, so copying also works from an SSH session.
GitHub PR browsing remains at `<leader>rg` (open) and `<leader>rP` (all).
